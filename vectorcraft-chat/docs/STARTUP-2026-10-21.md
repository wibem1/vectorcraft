Development only; version remains 0.3.1-dev. TODO reviewed before implementation. No release before verified real-engine results.

## Scope

Valid paid OpenRouter completion, provider-enforced cost caps and installable native packages remain separate open work.

## Implementation

- `app_connection.py` probes `engine.commands` on loopback and validates the response ID and VectorCraft command IDs. An occupied port with an incompatible/malformed/silent service is an error and never triggers a duplicate launch.
- Find the executable from the saved selection, `VECTORCRAFT_APP`, the chat/bundle folder, Windows Program Files/LocalAppData, macOS Applications bundles, or PATH. An absent installation invokes a one-time selection from the Tk main thread. Save the resolved path for later starts.
- On Chat opening, a background job connects or starts `[executable, --control, port]` directly without a shell. Windows uses CREATE_NO_WINDOW; POSIX starts a separate session. stdout is suppressed, stderr goes to the local startup log. The app remains open when Chat closes.
- A filesystem lock serializes startup across Chat instances. Probe again under the lock before spawning. A listening child that has not presented its first UI frame is allowed to become ready. Timeout or launch failure is reported; never kill a potentially useful native application or retry its launch blindly.
- Disable send/execute until a verified response. Port changes require a fresh connection. Connection loss disables construction; reconnect clears stale target IDs and proposals. A compact “VectorCraft starten / verbinden” button handles retry.
- The CLI bridge is also discovered beside the selected native executable. Triangle edits still use the verified shared engine module, now through actual remote TCP/MCP in the native test.
- `START-Windows.vbs` offers a console-free source entry point via Python's GUI launcher; Python/Tk and native VectorCraft/CLI are still installation prerequisites. No BAT is needed for application startup.
